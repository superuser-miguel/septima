The brotli archive that could only be opened on the machine that made it

2026-07-27 · engineering

Septima is a small thing: a GTK front-end that drives the 7zz binary from 7-Zip ZS. It doesn't reimplement compression — it builds the right command line and reads back what 7zz prints. That thinness is the whole design. It also means Septima inherits 7zz's bugs — and, if you're paying attention, catches them.

This is the story of one that would have quietly shipped corrupt archives to users, and how a single failing test caught it.

The trigger

In v0.3.0 we added Brotli, LZ4, LZ5 and Lizard as tar post-compressors — so you can make a real .tar.br in one gesture. Building the next feature (raw single-file streams), I wrote a round-trip test: compress a blob, extract it, assert the bytes come back identical. Every codec passed. Then brotli failed.

Isolating it

First guess: the compression level. I swept brotli levels 0–11 — all fine. So not the level. Same file, same everything, and yet the test built a .tar.br that 7zz itself refused to read:

7zz t out.tar.br
# ERROR: E_FAIL : Unspecified error

The difference between my passing manual test and the failing automated one turned out to be a single flag the app always adds: -mmt (multithreading, set to the CPU count). Drop it, and the archive is fine. Add it — any value, even -mmt=1 — and it's unreadable.

The twist: it isn't corruption

"Unreadable" sounded like corruption, but the data was intact. The stream is just coupled to the thread count it was created with:

7zz a -tbrotli -mx5 -mmt4 out-mt.br file

7zz t        out-mt.br     # ERROR: E_FAIL   (default threads)
7zz t -mmt4  out-mt.br     # Everything is Ok (matching threads)

So a multithreaded brotli stream can only be verified — or extracted — by passing the same -mmt back. And here's the part that makes it a real trap: the thread count came from the creating machine's core count. An archive made on a 12-core box needs -mmt=12 to open, with no hint of that stored anywhere. Move it to a laptop and it's a brick — a .tar.br that opens only on the machine that made it.

The inversion. The behaviour flips by context. Brotli inside a 7z container (-m0=brotli) works fine with threads — so Septima's shipped 7z-brotli was never affected. It's only the standalone -tbrotli stream (which tar → brotli and raw .br both use) that breaks with threads. Same codec, opposite thread behaviour.

The fix

A single-threaded standard .br is portable and reads anywhere, so the fix is to omit -mmt for the -tbrotli path — while keeping threads for 7z-container brotli, where they're both correct and useful:

// engine: build the -m* args
if let Some(threads) = self.threads {
    if self.format != "brotli" {      // the standalone -tbrotli case
        args.push(format!("-mmt={threads}"));
    }
}

Hunting it also surfaced a second, quieter bug from the same v0.3.0 work: the code that recognises "this is a compressed tar, browse inside it" had never learned .tar.br / .tar.lz5 / .tar.liz — so those archives, creatable since v0.3.0, couldn't be transparently opened. Fixed in the same pass.

Upstream

None of this is really Septima's bug — it's a sharp edge in how 7zz handles brotli threading. It's adjacent to already-closed upstream discussion (#351, #352), which documents that -mmt makes a brotli-mt stream "incompatible with standard brotli." The genuinely new bit is the failure mode: 7zz can't read its own output with default threads and reports a bare E_FAIL — no hint that -mmt=N is needed. We flagged that, respectfully — the maintainer runs this in his spare time.

Why a thin wrapper earns its keep

It would be easy to dismiss "just shells out to 7zz" as barely a project. But the thinness is exactly why this got caught: Septima's job is to build correct command lines and verify what comes back, and its test suite round-trips real archives through the real binary. That's what turned a silent, machine-specific corruption into a red test on a Tuesday — before a single user made an unopenable .tar.br.

The fix lands in 0.4.x, along with the rest of the 7zz CLI-parity work. If you're on the signed Flatpak repo, it'll arrive with flatpak update.
